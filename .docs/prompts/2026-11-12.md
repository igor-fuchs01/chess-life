## 6. List each route's request attributes in the controllers

**Prompt:**

> Nos controllers da API (`site-pessoal/src/controllers/`), documente em cada função que atende uma rota todos os atributos da requisição de que ela precisa para funcionar, deixando explícito de onde cada um vem: cabeçalho, corpo, caminho da URL ou query string. Não mude o comportamento nem os contratos da API.

**What was done:** Each of the 11 route handlers in the six controllers now has its method and path in its doc comment and one `@param` per value it reads, named by its source (`req.params`, `req.query`, `req.body`, `req.headers`) and starting with "URL path:", "Query string:", "Body:" or "Header:". The POST and PUT handlers also list the `Content-Type: application/json` header. The `registerUser` comment used to say the profile fields were optional; it no longer does, since only `abertura_favorita` is. Every controller passed `node --check` and loaded in Node. The convention is now in section 4 of `.docs/02-site-pessoal.md`. No code or reply changed, so `04-api.md` stays the same.

**Decisions:**

- Doc comments (`@param req.body.x`) instead of rewriting the code to read each value into a local variable — the request stays visible in one place above each function, the code and contracts do not change, and the validation helpers keep receiving `req.body`.
- The only header listed is `Content-Type: application/json`, on the routes with a body — it is what makes `express.json()` fill `req.body`; no controller reads any other header. The user id comes from the URL path, not from a header or the body.

## 7. Write the controller request docs in the style of .NET attributes

**Prompt:**

> Deixe a documentação dos atributos da requisição nos controllers mais profissional, com uma notação semelhante à do .NET (ASP.NET Core).

**What was done:** The doc comment of each of the 11 route handlers was rewritten with JSDoc tags named after ASP.NET Core attributes. Each comment has a one-line summary, then `@route METHOD /path`, then `@fromRoute`, `@fromQuery`, `@fromBody` or `@fromHeader` with `{type} name - description` (`[name]` when optional), then one `@response STATUS {type} description` per reply, and finally `@param req` and `@param res`. The file was regenerated with a script in the session scratchpad and kept in CRLF. Every controller passed `node --check` and loaded in Node. No code changed. The convention in section 4 of `.docs/02-site-pessoal.md` now describes this format.

**Decisions:**

- JSDoc tags instead of real attributes — plain JavaScript in Node has no attributes or decorators, and a build step or new dependency would break the project's rules. The tag names map one to one to `[HttpGet]`/`[HttpPost]`, `[FromRoute]`, `[FromQuery]`, `[FromBody]`, `[FromHeader]` and `[ProducesResponseType]`.
- `@response` lists each status with a short meaning, not the exact messages — the messages already live in `04-api.md`, and repeating them would let the two drift apart.
- XML doc comments (`/// <summary>`) were not used — editors only read JSDoc in JavaScript, so tags keep the comments useful on hover.
