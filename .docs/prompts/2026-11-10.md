## 2. Period filter on the dashboard, with its own controller

**Model:** Claude Opus 5.5, medium effort

**Prompt:**

> Coloque na dashboard um select para especifcar entre semana atual, semana anterior e data personalizada. Isso mudará diretamente as queries adicionando um condicional atrelado a data no where, a nova requisição deve ser feita sempre que for selecionada uma nova semana, no caso de data personalizada haverá um botão para realizar a requisição. A opção default assim que entrar na página deve ser a semana atual

> Crie um controller próprio para a dashboard, evite misturar com os outros controllers

**What was done:** The dashboard has a select next to the title with "Semana atual" (the default), "Semana anterior" and "Data personalizada". Choosing a week reloads the data at once; the custom option shows start and end date fields and loads when "Filtrar" is clicked. The data comes from two new routes, `GET /dashboard/tentativas/:idUsuario` and `GET /dashboard/listasExercicios/:idUsuario`, which require `?data_inicio=YYYY-MM-DD&data_fim=YYYY-MM-DD` and add the date condition to the `WHERE`. They have their own route, controller and model (`src/routes/dashboard.js`, `src/controllers/dashboardController.js`, `src/models/dashboardModel.js`), mounted in `app.js`. The page changed in `public/dashboard/dashboard.html`, `dashboard.css` and `dashboard.js`, and `04-api.md` (new section 7), `03-database.md`, `02-site-pessoal.md` and `01-project.md` were updated. The period validation was tested with fake requests, and the new routes and `GET /listasExercicios/listar` were called on the user's running dev server. They replied 200/204 with no SQL error, but user 1 has no attempts, so the filter was not checked against real rows. The page was not opened in a browser.

**Decisions:**

- At first the optional period was added to `GET /tentativas/listar` and `GET /listasExercicios/listar`. After the second message, those changes were undone and the dashboard got its own `/dashboard` route, controller and model. The user's choice: dashboard code is not mixed into the other controllers.
- The period is required on the `/dashboard` routes. The dashboard always sends one, so the controller has a single check and the queries always filter, with no conditional SQL.
- `GET /tentativas/listar` is no longer used by any page but was kept, so the contract does not break. `GET /listasExercicios/listar` stays as it was for the exercises page.
- The routes are `/dashboard/tentativas/:idUsuario` and `/dashboard/listasExercicios/:idUsuario`, named after what they return, because the controller has only one action per resource. They do not clash with the static `/dashboard/dashboard.html`, since `express.static` passes on paths that are not files.
- Custom period: a start-and-end interval, not a single day (user's choice). Like the weeks, it is just a pair of days, so the same query serves both.
- The weekly chart (last 8 weeks) became "Tentativas por dia", with one bar for each day of the period (user's choice). A filtered 8-week chart would show at most one or two bars.
- The "Acertos hoje" card became "Acertos no período", and the hit rate covers the period. Both show the period's dates instead of the comparison with yesterday or with the attempts until yesterday (user's choice). A comparison with the previous period was turned down because it would need a second request.
- Weeks run from Monday to Sunday, as `getWeekStart` already counted them. The last day is included with `data_tentativa < DATE_ADD(end, INTERVAL 1 DAY)`.
- The period is checked on the client (message under the title) and again on the server (`400` with `Informe a data de início e a data de fim.`, `Data inválida.` or `A data de início não pode ser depois da data de fim.`). An impossible day such as `2026-02-30` is refused, because `Date` rolls it over to March.
- `validatePeriod`, `isRealDay` and `parseId` live in `dashboardController`, following the project's pattern of keeping helpers inside each controller.
