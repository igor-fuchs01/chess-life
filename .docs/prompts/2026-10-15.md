## 2. Dashboard based on games played on the site, with a games API that identifies the opening

**Prompt:**

> esse dashboard deve se basear nos jogos jogados pelo usuário, a ideia é ter uma api que avalia a abertura feita e registra isso no banco de dados a partir da partida do jogo de xadrez dentro do site, juntamente disso é melhor ter um gráfico de partidas por semana, e nas estatísticas devem realmente mostrar como kpis que dão informações relevantes como comparação de partidas no dia passado, porcetagem de vitória total em comparação ao dia passado e abertura favorita. O título do dashboard também deve ser pertinente as informações apresentadas

Answers to the clarifying questions: remove the manual form; "A ideia é dentro do servirdor mysql possuir uma tabela com a partida registrada, os movimentos, a abertura e algumas outras informações referentes a partida"; build the API and the dashboard now, and the game page later.

**What was done:** Built the `partida` API (`src/routes/partidas.js`, `src/controllers/partidaController.js`, `src/models/partidaModel.js`, registered in `app.js`). It lists, registers and deletes games, and identifies the opening from the moves with `src/models/openingBook.js`. `database.executar` now accepts values for `?` placeholders (`src/database/config.js`), and the `partida` table was added to `script-tabelas.sql`. The dashboard (`public/dashboard/`) is now "Meu desempenho no xadrez". The manual form is gone, and the page has three KPIs (games today vs. yesterday, total win rate vs. until yesterday, favorite opening with its games and win rate), a stacked games-per-week chart, the results and openings charts, and the games table with color. Updated `.docs/project.md` and `.docs/site-pessoal.md`. Checked with Node: opening identification on 9 sample games, controller validation with a stubbed database, and `dashboard.js` run against a mock server with sample games, where every KPI and chart value matched the hand-computed numbers. Not tested in a browser (the Chrome extension was not connected) or against MySQL. Nothing calls `POST /partidas/cadastrar` until the game page exists. Nothing was committed.

**Decisions:**

- Games are not typed in by hand: the dashboard shows only games played on the site — the user chose to remove the form.
- The `partida` table stores `resultado`, `adversario`, `cor`, `lances` (SAN joined by spaces), `abertura` and `data_partida` (DATETIME set by the database) — the user asked for the moves, the opening and other game details in MySQL. Color was the extra detail chosen because it matters for openings. The database setting the date satisfies RN05 without a client date.
- The opening is identified on the server from a list of about 50 openings in `openingBook.js`, picking the longest matching move sequence — no new dependency and works offline. Discarded: the Lichess opening explorer (external service, may need a token).
- The server checks the SAN format of each move but not its legality — legality needs chess.js, which the game page will use (RF14).
- Delete became `DELETE /partidas/deletar/:idUsuario/:idPartida` and only deletes the user's own game (RN03), instead of the planned `/deletar/:idPartida`. The planned contract had never been built.
- The win-rate KPI compares the rate of all games with the rate of the games played until yesterday, in percentage points — the reading of "porcentagem de vitória total em comparação ao dia passado".
- Weekly chart: last 8 weeks starting on Monday, stacked by result. It replaces the monthly line chart, and the extra split by result costs only two more datasets.
- Back-end functions are named in English (`listGames`, `registerGame`, `deleteGame`) following the language convention, while files, routes and columns keep the Portuguese resource name already documented (`partida`).
